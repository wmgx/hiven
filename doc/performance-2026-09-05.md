**hiven 性能基准与优化报告 · 2026-09-05**

在固定合成数据基准中，导航排序耗时降低约 96%，收藏较多的命令排序降低 96.7%。本次只改动两个运行时代码文件；六组基准输出的结果与顺序全部一致。

基线提交：`1c1ceaed63b81aade8ea0f01dea23eb5a06c3675`。环境为 Apple M3 Pro、macOS arm64、Node v22.22.2；依赖沿用现有安装。原始样本、环境信息、结果指纹见 [优化前数据](performance-2026-09-05-before.json) 和 [优化后数据](performance-2026-09-05-after.json)。

最初检查现有 Launcher 埋点：最近五次打开中有四次首帧数据，p50 为 119 ms，范围 66–138 ms，每次会话出现 10–34 次排序。这只是定位线索，不能与下面的合成基准或浏览器首帧直接比较。

**排序基准（单位：ms，越低越好）**

| 场景 | 优化前 p50 | 优化后 p50 | p50 降幅 | p95 前 → 后 |
|---|---:|---:|---:|---:|
| 300 命令，空查询／30 收藏 | 0.309 | 0.078 | 74.9% | 0.351 → 0.157 |
| 300 命令，英文搜索／30 收藏 | 0.451 | 0.301 | 33.3% | 0.514 → 0.333 |
| 300 命令，中文拼音／30 收藏 | 0.566 | 0.442 | 22.0% | 0.591 → 0.480 |
| 300 导航候选，空查询／30 收藏 | 18.858 | 0.727 | 96.1% | 20.821 → 0.912 |
| 1000 导航候选，搜索／100 收藏 | 215.784 | 8.714 | 96.0% | 250.297 → 9.589 |
| 1000 命令，空查询／200 收藏 | 6.467 | 0.214 | 96.7% | 6.854 → 0.246 |

脚本通过 Vite SSR 加载实际排序、匹配和拼音实现，使用固定时钟、固定标题和收藏集合，不读取个人历史。每组预热 20 次，然后记录 40 个样本，每个样本取 5 次调用的平均耗时。p95 是这些均值的分位数，不是单次用户请求的尾延迟。导航数据中 75% 为标签、25% 为窗口，标题不相似，用于覆盖必须遍历候选的场景；1000 项是压力场景。

定位和改动如下：

1. 收藏数组此前在每个候选计分、部分空查询过滤中反复转为 Set；现在每次排序只转换一次。现有回归检查构造次数为 1，并验证数组和 Set 输入的排序一致。
2. 最高导航层级的标签不可能被更高层级结果降权，却仍扫描所有候选；现在立即返回。
3. 前两项优化后，1000 导航候选仍需 197.35 ms。对 15 次排序的 CPU 采样发现约 92% 的时间记录在标题规范化函数中。现在通过 WeakMap 按候选对象复用规范化标题，原始标题变化时重算；候选回收时缓存可自动释放。基准脚本同时检查标签标题和窗口标题突变，确认降权结果随之更新。

近似标题比较仍保留原来的 O(n²) 最坏复杂度。本次消除了重复字符串处理，没有引入候选索引或调整排序规则。动态结果到达时的排序次数未在本次减少。

**浏览器对照（单位：ms）**

共享工作区有其他任务同时修改插件，因此最终浏览器数据来自基线提交的隔离快照，优化后仅覆盖本次两个运行时文件。同一目录、同一 HTTP origin，分别构建生产版本。每阶段使用 10 个全新 browser context，复用同一 Chromium 进程，本地 HTTP，无网络或 CPU 限速。

| 场景 | 优化前 p50 | 优化后 p50 | p95 前 → 后 |
|---|---:|---:|---:|
| 启动到输入框后的双 rAF | 174.0 | 185.0 | 242.0 → 271.8 |
| 首次内容绘制 FCP | 176.0 | 188.0 | 244.0 → 276.0 |
| 搜索 input 事件后的双 rAF | 12.2 | 12.0 | 18.0 → 18.3 |
| 首次打开 Quick Editor | 414.3 | 417.7 | 873.5 → 882.2 |

Chromium：`147.0.7727.15`。初始 JS 解码体积为 3,595,876 → 3,596,119 字节（+243 字节）。启动未观察到改善：输入框帧指标中位数增加 11 ms；10 轮样本不足以将这种小幅差异归因于改动。编辑器指标也未确认收益。

input 后双 rAF 只衡量帧响应代理，不代表异步搜索结果全部返回。每轮验证搜索有候选、方向键有唯一选中行、Quick Editor 可打开并输入文本；最终 10 轮全部通过，无 pageerror，并检查了实际截图。原生全局快捷键、WebKit 唤醒和后台恢复未进行受控前后复测，因此不声称原生首帧降低 96%。

在仓库根目录执行排序基准，第三个参数会核对历史结果指纹：

```sh
node scripts/benchmark-launcher.mjs temp/ranking-latest.json doc/performance-2026-09-05-before.json
```

浏览器基准使用现有 Python Playwright 与 Chromium。先启动生产预览，再在另一终端运行：

```sh
npm run build
npm run preview -- --host 127.0.0.1 --port 4176
python3 scripts/benchmark-launcher-browser.py http://127.0.0.1:4176 temp/browser-latest.json
```

基准不设置绝对耗时失败门槛；排序结果变化会直接失败。对代码继续优化时，应在同一机器、依赖和输入下保留前后原始样本。
