# 产品定位反方：对抗脑暴（07-adversarial-2-product）

> 立场：专挑《Hiven 探索结论报告》（下称"报告"）的产品判断下手，提出反命题。
> 方法：先 steelman 原结论（不许稻草人），再攻击；每个攻击标注证据等级///；每个反命题给出"如果我对了，产品该怎么做"。
> 仓库只读，未改动。

## 先认的：扎实、不攻击的部分

1. 三种"质疑定位式"重构被证伪（常驻工作台回摆 / 插件真沙箱 / 换渲染方案）——技术评估的量级论证扎实，收益确实覆盖不了成本。
2. 质量门禁在 main 上变红是最痛的技术债——，无可辩驳。
3. 不做全局 AI 聊天框——与 quiet/precise 定位和 150ms 预算确实冲突。
4. behavior observation（桌面截图+键盘记录）冻结——信任成本论证充分，自学习现有产出确实不依赖它。
5. launcher-only 对**真·one-shot 任务**（uuid、时间戳、算式）成立——热键直达是正确形态。

下面攻击的是报告**过度推广**了这些成立的判断的地方。

## 攻击 1：launcher-only 教条化——"暂存、对照、反复看"的任务被系统性亏待

**靶子**：报告 §3.1 "launcher-only 不应质疑" + §0 "不应推翻"。

**Steelman**：文本变换多为秒级短任务，常驻主窗口增加"打开应用"的心理成本；退役是三个月前深思熟虑的转向（有完整设计文档）；逆转=自我否定，回摆成本 2–4 人周且收益未经证实。

**反命题**：教条成立的范围被夸大了。文本任务不是只有"洗一下"，还有一整类** staging 型任务**——暂存、对照、反复看：
- diff 两段各 200 行的日志，需要两边同时可见、反复滚动对照几分钟；
- 长 JSON 先折叠浏览、再决定美化哪一段；
- 一串未知编码，多次尝试不同解码并排对比中间结果（正是 CyberChef 用 recipe 解决的场景）。

这类任务的共同点是**文本需要"住"在工具里一段时间**，而不是"路过"剪贴板。launcher 的瞬时 popup 天然不适合"住"。

**证据**：
- 报告自己也承认产品**已经**有持久 surface：text-diff / clipboard-history 是独立窗口，Quick Editor 可 detach 为独立窗口。"launcher-only"很大程度上是品牌叙事，现实是"launcher + 若干持久插件窗口"的混合体——教条与现实已经脱节，攻击的不是现实而是教条。
- 设计视角发现 DESIGN.md 写 Quick Editor 是 "single editor（no multi-pane split）"，实现里却有完整多 pane 分屏（`paneOrder`/`splitDirection`/`⌘\`）。团队自己在**反复重新发明**持久多窗格——这是真实需求在顶教条的证据。
- Boop 是常开窗口模型（文本住在工具里）；CyberChef 的 recipe 让整条链同时可见。两者服务的正是 staging 型任务。
- 报告的"3 步"数学注水了："复制→热键→Enter"没算**校验**步。真实流程是 复制→热键→（看推荐对不对）→Enter→（看结果对不对）→粘贴。对 200 行日志，用户必须先打开 Quick Editor 看全文——这是第 2.5 步，报告没算。Object Block 只给 `[预览文本 · kind · 来源 ×]` token，操作的是盲文本。

**如果我对了，产品该怎么做**：不复活全功能工作台（那确实是自我否定），而是把 **Quick Editor 从"可 detach 的配件"升格为一等持久暂存面**：launcher 加一键"暂存到编辑器"；staging 型任务（diff 长文本、多步链）默认落到编辑器/diff 面板而非瞬时 popup；补上 DESIGN.md 与实现的口径（承认分屏或砍掉）。一句话：launcher 负责 one-shot，编辑器负责 staging——分工写进定位，而不是用"launcher-only"一句话盖住两种任务。

## 攻击 2："B 为二等公民"——断了获客，A 再强也没人装

**靶子**：报告 §3.1 "A 为主、B 为二等公民；窗口/进程/飞书停止投入"。

**Steelman**：B（桌面启动与控制）是 Raycast/Alfred 的主场，Hiven 无差异化；README 自相矛盾（又说不做全能 launcher 又列 App/窗口/进程为主要能力）；feishu 依赖 lark-cli；08-09 冻结要求先收敛。

**反命题**：**没有人会为"洗文本"装一个 launcher。** 获客漏斗是：用户因为"替代 Spotlight/Alfred 打开应用"（每天 50+ 次的热键习惯）装上 → 在同一个热键习惯里**顺手发现**文本变换。Raycast 就是这么赢的：app 启动 + 窗口管理 + 剪贴板历史是留存钩子，1000+ 扩展（含文本工具） riding 在装机量上。DevToys/Boop 已经零热键成本地服务了"洗文本"需求，Hiven 凭什么让用户多装一个常驻应用？凭的只能是"你每天已经按 50 次这个热键了，顺手洗个文本吧"。

报告自己写了"保留 App/URL 快打开（这是 launcher 的入场券）"——**一边承认 B 是入场券，一边判 B 二等公民，这是自相矛盾的**。入场券如果是二等的，门都进不来：一个偶发丢按键、排序抽风的应用启动器，会在用户发现任何文本功能之前就被卸载。

**证据**：
- Raycast 的增长路径是 launcher-first + extension 生态；其文本相关能力（Quick AI、no-view）全部长在 launcher 习惯上。
- 报告自己的"入场券"表述与"二等公民"并存，逻辑不自洽。
- 获客漏斗主张（"为洗文本装 launcher"意愿弱）待验证——但举证责任在报告这边：0 stars 的产品谈"聚焦 A"，默认了用户会来，而用户为什么来恰恰是未解问题。

**如果我对了，产品该怎么做**：改的不是"投不投 B"，而是**二等的是"投入广度"，不是"质量标准"和"叙事位置"**。App/URL 启动的质量必须是一等的（速度、排序、frecency，一个都不能抽风）；窗口/进程保持"够用不扩张"；feishu 见攻击 5。叙事上翻转：对外讲"最快的 launcher，顺手把文本洗了"，而不是"文本工作台，顺便能开应用"。前者有获客故事，后者没有。

## 攻击 3："accepts 覆盖率做到极致"——边际递减，且在加深信任债

**靶子**：报告 §3.2 方向 1 "内容感知覆盖率做到极致…投入产出比最高"。

**Steelman**：零 AI、零隐私风险、符合定位；"少搜命令名"是作者定的成功标准；line-tools/crypto/csv/random 无 accepts 是明确缺口。

**反命题**：边际收益递减，且方向错了半步。
1. **数学**：极致化省的是"复制→热键→**搜两个字母**→Enter"里的"搜两个字母"。而每多一个 accepts 声明，就多一份**误推荐风险**：排错第一的代价（用户识别错误→下移→重选→信任受损）远大于打两个字母。报告自己的设计章节把"排序零解释"列为 P1 信任问题——在零可解释性的排序上加码推荐，是在信任的窟窿上继续挖。
2. **Head/tail 分割**：a-ha 时刻"复制→热键→它已经知道你想干什么"需要用户（a）记住全局热键、（b）养成"先唤起再想"的习惯、（c）信任首条结果。这套学习成本只对 top ~10 高频意图（base64 解码、JSON 美化、时间戳）划算；line-tools 第 23 个工具（SQL-IN 生成器）用户一辈子形不成条件反射，永远会搜名字。"极致"是错的目标。
3. **frecency 已经解决了尾部**：每周用一次"转 SQL-IN"，frecency 会在你输入 `sql` 时把它排第一。为低频工具补 accepts 的边际价值 ≈ 0。

**证据**：
- `ranking.ts` 权重体系 + frecency 已存在（报告 §3.2 自己引的）。
- 报告设计章节 P1"排序零解释"——推荐越激进，可解释性债越重。
- 学习成本与 head/tail 分割待验证——但**验证数据现成就有**：`~/.local/hiven/logs/launcher-perf.ndjson` 里 `behavior:object_action.execute`（推荐命中）vs 搜索选中率，按意图分桶一看便知。报告没读就定了 P0。

**如果我对了，产品该怎么做**：把方向 1 改写为"**head 意图覆盖 + 可解释性优先**"：accepts 只补 top 高频意图（用作者自己的 telemetry 定名单）；给每个 accepts 声明设验收线（推荐接受率低于阈值就降级为普通搜索结果）；尾部交给 frecency + 别名/拼音搜索（已经做得不错）。P0 从"补齐 accepts"换成"排序可解释性"（报告 §3.4 的 P1 升 P0）。

## 攻击 4："选中即行动"新入口——双入口、双心智，证据还不够硬

**靶子**：报告 §3.2 方向 2，新增全局热键抓取选中文本弹动作面板。

**Steelman**：uTools 超级面板 / Alfred Universal Actions / Raycast no-view 三方共识；5 步压到 3 步；与现有唤起"互补不替代"。

**反命题**：
1. **"互补不替代"没回答决策成本**：用户将拥有**两个热键**——唤起 launcher 的，和抓取选中的。在"编辑器里选中一段文本"这个重叠场景，两个入口都work，用户每次都要做选择。Alfred 之所以成立，是因为它只有一个内容热键（Universal Actions）+ 一个搜索热键（⌘Space），分工 crisp："有选中就按前者，否则后者"。报告没给出 Hiven 的 crisp 分工规则。
2. **"竞品共识"注水了**：uTools 超级面板（鼠标中键）是中文用户特有习惯，05 号报告自己标注了二手转述待验证；Alfred Universal Actions 是 macOS 付费极客圈；**Raycast 恰恰没有做通用 select-and-act 面板**——它的答案是 per-command no-view 热键 + Quick AI。真·跨地区的共识其实是 DevToys 式的**剪贴板感知**（clipboard-aware），而这正是 Hiven 已有的 Object Block。
3. **实现是可靠性 minefield**：跨平台抓取前台选中文本（macOS 走 accessibility API，Windows 靠模拟 Ctrl+C 劫持剪贴板）在终端、虚拟机、密码框里会静默失败。"有时灵有时不灵的热键"是最差 UX。报告把它当成一个普通功能点计价，漏了可靠性成本。

**证据**：
- Raycast no-view = 逐命令热键（Easydict `⌥A`），非通用面板；05 号报告原文可查。
- uTools 超级面板细节为二手转述（05 号报告已标注待验证）。
- `attachPolicy` 已规定"剪贴板只能经 Object Block 进入"——选区是同一条路缺的另一半，不需要新路。
- 抓取选区的跨应用 flaky 程度（业界公认，标假设）。

**如果我对了，产品该怎么做**：**不加第二个全局热键**。改为让**现有唯一热键具备选区感知**：唤起时若前台有选中文本，自动挂载为 Object Block（"热键永远作用于当前选中的东西，没有选中才用剪贴板"）——一条 crisp 规则，零新概念，拿到 80% 的省步数。把省下的精力投到这一条路的可靠性（各应用抓取成功率 telemetry）。真要做独立面板那天，它必须**取代**而非并行选区场景。

## 攻击 5：feishu 之死——用抽象定位杀死唯一真实用户的真实需求

**靶子**：删减清单 #1 "feishu 降级为默认关闭的可选插件：与定位最远"。

**Steelman**：与"精确文本工作台"定位最远；依赖本机 lark-cli 门槛高；08-09 冻结要求先收敛不扩广度。

**反命题**：报告 §2 自己承认——这个产品**唯一的真实用户是作者本人**（0 stars，单贡献者，全靠 dogfooding）。对 dogfooding 驱动的产品，"定位最远"是抽象，"作者每天用不用"才是地面实况。如果作者每天用飞书搜文档/联系人 20 次（飞书是国内开发者的日常工作台，这个假设很合理），那么默认关闭 feishu 就是**为了服务一份定位文档而伤害唯一真实用户的日常体验**——本末倒置。

更进一步：feishu 可能不是"偏离"，而是**唯一的护城河**。Raycast/Alfred 在中文市场恰恰缺本土 IM/办公生态集成；uTools 在国内赢的一部分原因就是本土化集成。"中文职场人的 Raycast"（飞书/企业微信/钉钉/浏览器深度集成）是一个 Hiven 能讲、Raycast 讲不了的故事。报告把它框为"偏离"，可能是把差异化当成了噪音。

**证据**：
- 报告 §2：0 stars、单作者、"验证对象只有作者本人的 dogfooding"——第一用户是作者，这是报告自己的结论。
- `~/.local/hiven/logs/launcher-perf.ndjson` 的 `behavior:launcher.item_select` / `behavior:launcher.query_change` 能直接回答"作者用 feishu 的频率"——**数据存在但报告没读**，就判了死刑。这是程序不正义。
- uTools 本土化集成是其国内立足点之一。
- 作者的 feishu 使用频率、护城河主张。

**如果我对了，产品该怎么做**：**先读数，再判刑**。读作者自己的 telemetry（这是他自己的数据，无隐私问题），feishu 调用频率/接受率摆出来：高频 → 不仅不降级，反而把"中文工作流集成"立为第二支柱（飞书→企业微信/钉钉/浏览器收藏夹），写进定位；低频 → 那时再默认关闭，我认。以及 lark-cli 门槛是真的，解法是降低配置成本（向导式绑定），不是砍功能。

## 攻击 6（元攻击）：零用户的产品，排什么 P0 路线图？

**靶子**：报告 §2 "任何大投入之前，都需要第一个外部真实用户" vs §3.2/3.4/3.5 的一串 P0。

**反命题**：报告同时说了两句话——"别为一个人优化"和"这些是 P0 方向"。执行层会按后者真投。0 stars 产品的诚实优先级第 0 位是**验证与分发**，不是"把 accepts 补到极致"。方向 1–5 里除了修门禁和修 lockfile（那是 hygiene），其余都该裱起来写成"实验 + 杀线"：比如"补 10 个 head accepts，若推荐接受率 < X 则停"。否则这份报告就是一份给成熟产品的路线图，套在一个没用户的产品上。

**如果我对了**：报告 §3.2 每个方向补"验收标准/杀线"；新增第 0 优先级：release 恢复（3.5 个月没发布了）、License 声明、第一个外部用户获取实验。先让 10 个人装上，再谈"每天打开"。

## 杀伤力排序

1. **攻击 2（B 二等公民）**——战略级。若错，产品没有获客故事，后面所有优化都是给空气优化。断的是生路。
2. **攻击 6（元：P0 vs 零用户）**——执行级。若错，团队把稀缺精力投进"极致化"，错过验证窗口。
3. **攻击 5（feishu 误杀）**——伤害唯一真实用户 + 可能误杀护城河；且程序不正义（数据没读）。
4. **攻击 1（launcher-only 教条化）**——staging 型任务被系统性亏待；"3 步"数学注水让 ROI 计算失真。
5. **攻击 3（accepts 极致化）**——P0 力度错配 + 加深信任债；但做也是有用功，伤害有界。
6. **攻击 4（双入口）**——加法项，可被单热键方案替代；伤害可逆，排最后。

## 必须修改的结论（3 处）

1. **§3.1 "A 为主、B 为二等公民"** → 改为：**二等的是投入广度，不是质量标准与叙事位置**。App/URL 启动质量必须一等（这是入场券）；叙事上 B 是获客、A 是留存/差异化。删掉"飞书深度集成停止投入"里的 feishu 部分，转攻击 5 的"先读数"。
2. **§3.2 方向 1 "覆盖率做到极致"** → 改为：**head 意图覆盖 + 可解释性优先**；accepts 设接受率验收线，尾部交还 frecency + 搜索；把 §3.4 的"排序可解释性"升为 P0。
3. **删减清单 #1 feishu 默认关闭** → 改为：**冻结处置，先读作者 telemetry**；在拿到 `behavior:launcher.item_select` 中 feishu 占比数据前，任何"默认关闭"都不执行。同时把"中文工作流集成作为潜在第二支柱"列为待验证假设，而非已证伪方向。

## 可证伪我的判据（留给正方）

- 读 `~/.local/hiven/logs/launcher-perf.ndjson`：若 feishu 的 item_select 占比 < 5% 且作者主观确认低频 → 攻击 5 撤回。
- 同一日志按意图分桶统计 `behavior:object_action.execute` 接受率：若长尾 accepts 接受率 > 60% → 攻击 3 撤回"极致化"部分。
- 若作者能说出 3 个"为洗文本而装 launcher"的真实用户画像 → 攻击 2 降级。
