剪贴板专属能力，还是通用能力？

代码里 LauncherObjectBlock 的 source 已经统一了 clipboard / editor-selection / history-item / tool-result 等多种来源，全部落到同一个 payloadText 字段。 「大爆炸」如果只吃 payloadText，天然就是一个不挑来源的通用动作—— 剪贴板只是触发最频繁的入口，不代表它该被焊死在剪贴板里。

建议：把它做成任意「文本形态 Object Block」在 kind 为 text / plain-text / markdown / query-string 等时的推荐动作，剪贴板 Object Block 是当前唯一会挂它的地方， 但编辑器选区、历史项、工具结果这些入口不需要额外改造就能直接复用。

为什么还需要「手动触发」入口

查了 attachPolicy.ts：剪贴板 Object Block 的自动挂载有意收紧到 STRONG_ATTACH_CONTENT_KINDS（json / url / jwt / csv / secret 等）， 纯文本 / 长段落被显式排除——注释原话是「generic text … is intentionally not a gate」。 「recent clipboard hint」（30s–2min 的兜底提示）同样复用这条门槛，所以纯文本目前完全没有 自动进入 Object Block 的路径。

而「大爆炸」最典型的输入恰恰是这类纯文本段落（一句话、一段话里挑几个词）—— 如果只挂在入口 A，产品上线后大概率永远看不到它。入口 B（上图，Global Launcher 里可搜索的独立命令） 选中后不读剪贴板，而是塌缩成蓝色命令 token，后面接一个真实文本框让你手动输入或粘贴—— 跟现有「命令 token + 参数」的输入行范式一致（沿用 launcher-token-interaction-direction 已拍板的 token 输入行样式），两个入口共享同一套拆分 / 选择 / 上屏逻辑。

链接要不要也炸开

建议炸，而且默认直接炸，不做「先折叠成一个链接 chip、再点开」的二段式。demo 里的 URL 已经改成 按结构拆：origin（https://code.byted.org）一整块，path 每一段（repo / merge_requests / 128）各自成独立碎片，query 的 key/value 也拆开——同时用 一圈浅蓝虚线把同一条链接的碎片框在一起，保留「这些碎片来自同一个链接」的可读性，同时每一段仍然可以单独拖选。

这样做的直接价值：复制一条 GitLab MR 链接，只想要 128 这个号码，或者只想要 repo 仓库名——不用手动数斜杠，拖一下就选中了。跟已经在做的 URL 模板自学习（urlTemplate.ts 的 templatizeUrl/变量槽归纳）也是同一挂钩点：大爆炸选出来的 128 就是那个「变量槽」， 后续两边可以互相印证。权衡是链接一多，画布会更碎——如果实测觉得吵，可以退回「origin 保持整块 chip、 点一下才展开 path/query」的折中方案。
