# hiven「懂你」场景分析（2026-10-17）

目的：用户自己说不出具体场景，所以从本机数据推断**你打开 launcher 那一刻最可能想要什么**，作为「懂你」设计的依据。

## 推断出的主要场景（按频率 × 改进空间排序）

### S1 把 AI 的输出搬进工作里（ChatGPT 占复制来源的 21%）
从 ChatGPT/Codex 复制回答，再粘进飞书、终端或 GoLand。痛点是 Markdown 符号、代码围栏、命令里的提示符。
- **打开即就绪**：如果剪贴板来自 AI App，第一行就是按前台 App 清洗好的版本：飞书用富文本，终端只留命令行，GoLand 只留代码块。Enter 直接粘回去。
- 现有资产：line-tools 的「Clean Agent 文本」（用得很少，因为要自己去找）。

### S2 浏览器和飞书里的工程标识 → 内部平台（Edge + 飞书 = 64%）
复制的多是短内容（中位数 31 字节）；favicon 缓存里大量是 cloud / data / code.byted.org 这类内部域名。网站快开规则一共用了 113 次。
- **打开即就绪**：剪贴板里是 logid、PSM、MR 链接或时间戳时，第一行就是对应的直达动作，比如「在 Argos 查这个 logid」「在云平台打开这个 PSM」，或者时间戳换算成本地时间。
- 现有资产：web-open 快开规则、时间戳、URL 识别。缺的是：**把剪贴板内容作为参数注入快开规则**。

### S3 离开工位 / 切换状态（锁屏 257 次、VPN 29 次）
锁屏是使用最多的单个动作，频次排序已经把它排在第一。**不需要重新设计**，只要保证空查询时它稳定排第一、响应不卡就行。

### S4 卡住的开发进程（结束进程 33 次）
[推断] 多半是端口被占用或开发进程挂住了。
- **直答**：输入端口号（比如 `1420`），直接给出「结束占用 1420 端口的进程」；输入进程名，列出匹配的进程，并附上端口和 CPU 信息。

### S5 截图和图片（占复制的 13%）
图片复制现在几乎没有任何处理（只有扫二维码）。
- **打开即就绪**：剪贴板里是图片时，第一行就是图里的文字（macOS Vision OCR 本地运行，毫秒级）；如果图里有二维码，第一行是二维码内容。
- 收益仅次于 S1：数据量不小，全程本地、速度快，不用等 AI。

### S6 编码与结构化文本（Base64 40 次、JSON 25 次、计算器 42 次）
阶段 B 已经实现了「内容直达动作」。**保持又快又准就够了**，不需要新设计。

### S7 剪贴板历史基本没被用起来（6%）
数据很多，但用不上。
- **按上下文召回**：在 GoLand 里打开时，优先显示最近从 ChatGPT 复制的代码和命令；在飞书里打开时，优先显示最近的链接。不要把历史平铺成一大串。

### 删除后消失的
飞书联系人搜索用过 35 次，频率不低。本轮按用户的决定已经删除，这里只记录事实。

## 这些场景共用的「打开即就绪」机制

```
按下热键
  → 信号（本地，< 10ms）：前台 App、剪贴板的类型 + 来源 App + 新鲜度、选中文本、
     「猜你想干」历史（需用户开启；记录你在哪个 App 里用过哪些动作）
  → 预测排在前面的 1–3 个动作
  → 立刻在本地预算结果（清洗、OCR、时间戳、带参数的 URL），第一行就是结果本身
  → 只有用户明确开启的 AI 动作才会预取（比如翻译）
  → Enter = 按目标 App 需要的格式送回原 App
```

「猜你想干」（context suggestions）已由用户批准作为信号来源之一（2026-10-17）。

## 建议的下一步

1. 先做 S1（AI 输出清洗 + 按目标 App 粘回）和 S5（图片 OCR）两个场景。两个都是高频、全程本地、不用等 AI。
2. 然后做 S2（剪贴板内容注入快开规则）。
3. 再做通用的「空查询第一行预测」机制，接入「猜你想干」数据；之后再考虑 L2 本地语义检索。
